Behaviors marked "probe" were executed under Lune 0.10.5 against the legacy shim (`P/reference/lune/Tick.luau`), rxi `tick.lua`, and the prior build. Scripts and raw output: `W/research/scratch/semantics-spec/{legacy_probe,legacy_probe2,prior_probe}.luau` (run with `lune run <file>` from that directory). Probe ids (L1..L17, R2 double-tick, P1..P18) are referenced in the table.

Terms used below: **scheduler** = one instance (what rxi calls a group); **now** = the scheduler's own accumulated clock; **due** = absolute fire time on that clock; **base** = the due of the entry whose callback is currently running; **seq** = per-scheduler monotonically increasing arm counter used as the equal-due tie-break; **terminal** = Fired or Stopped.

Handle states carried over from prior (`Handle/init.luau:22-28`): Pending, Paused, Chained, Fired, Stopped. TickRevamp adds no new state; it adds one flag (`pausedWhileChained`, row A8) and one transient guard (`completing`, row F6).

## Non-negotiables (any correct implementation)

1. `update()` processes only the due prefix of a (due, seq) min-heap; an idle scheduler costs one peek. Same-due entries dispatch in arm order (C4).
2. A one-shot is Fired BEFORE its callback runs; a recurring is re-armed at `due + period` BEFORE its callback runs. Inside its own callback `h:getState()` reflects that (S1).
3. `stop`/`remove`/`Destroy` on a handle never fires it, is idempotent, is terminal, never touches scheduler state after the first call, and cascades Stopped to Chained children (S1, S2, S4, S5, A1, A2).
4. A handle stopped from inside any callback - its own or another's - never fires again in that update, even when lagging (S2, S3, F5). No entry is ever advanced twice.
5. A stopped, fired, or destroyed handle is never resurrected by reset/adjust/resume/after/complete (S4).
6. `update(dt)` rejects NaN, negative and non-number dt before touching state; creation rejects NaN/inf/negative delays and 0-period recurrences (I2, I4, I10, I11, I13).
7. Every callback runs under `xpcall` with `debug.traceback`; one erroring callback never prevents the others in the pass, and an erroring OnError handler never propagates (E1, E3).
8. Timers created inside a callback on the same scheduler are measured from the firing entry's due; a past-due nested timer fires later in the same update, never synchronously inside `delay()` (C1, C2, C3).
9. Explicit operations (reset/adjust/resume/complete) are measured from `now`, never from the firing entry's due (R5, R6, R10).
10. `adjust` preserves the consumed fraction (`due' = now + frac * newTotal`) and never produces NaN (R1, R3).
11. `complete()` fires exactly once, transitions like a natural fire, returns a boolean, and is a no-op returning false on a terminal handle (F2, F5, F7, F8).
12. Chained children can be stopped before the parent fires, are armed in registration order from the parent's due, and inherit Stopped from a stopped parent (A1, A2, A6, A9).
13. `pause` freezes the current cycle; a paused recurring accumulates no missed fires; pause/resume on the wrong state is a no-op, never a raw internal error (R8, A8).
14. A scheduler's `Destroy()` (including from inside its own update) fires nothing further, stops every handle, unbinds its hook, and makes later `delay/recur/update` error; it never crashes the pass (N4).
15. Scheduler public methods accept both `s.delay(...)` and `s:delay(...)`; handle methods are colon-only with a clear error on dot misuse (S8, S9).
16. The scheduler holds handles strongly until they reach a terminal state; a recurring timer therefore never dies unless stopped - this is documented at the top of the API doc (O4).
17. `TickAPI.Tick`, `TickAPI.Tickh`, `TickAPI.SafeStopClock`, `TickAPI.GetAfterNotTouched`, `TickAPI.Tickr` (nil on the server), `h:stop/reset/after/adjust` keep their live call shapes (H1, H5, S6).
